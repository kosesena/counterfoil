A merchant-side gate between an AI payments agent and the payment rail. Every refund or charge the agent attempts is checked against the store's own records (return authorisations, order totals, ownership) before money moves. Pick an email, run it under three conditions, and watch what each one lets through.

HOMI · return of order ST-1057

1 · The email

Live mode only. Your email is read by the Reader agent against the fictional store below; no order outside it can be touched, whatever the email says. Try hiding an instruction in the HTML part.

The store's records (what the gate checks against)

2 · Run it

The Reader sees the raw email and hands off a fixed set of fields. The payments agent never sees the email, only that hand-off, and makes tool calls. Each call goes through the condition's gate before it may reach the rail (a mocked Braintree/PayPal). All three conditions share one Reader output, so they differ only in the gate.

3 · Buy it for real with PayPal, then let the agent refund it

This step is real money movement in the Braintree sandbox (PayPal's payment platform, test money). Pay for the selected scenario's order with the PayPal button. Then the agent's recorded refund calls for that scenario are sent through a gate onto your transaction: the gate decides now, and anything it lets through is a real sandbox refund of your purchase. No model runs here, so this costs nothing.

PayPal accounts cannot be opened from Türkiye, so this sandbox has no linked PayPal login. The PayPal button pays with Braintree's mocked PayPal account (fake-paypal-one-time-nonce): a real sandbox transaction whose instrument is paypal_account. The card option uses Braintree Drop-in with a test card (4111 1111 1111 1111, any future date).
