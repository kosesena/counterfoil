# Codex code review — core (23 Oct 2026)

`codex exec -s read-only`; raw output.

Read-only review complete; I did not change any files and did not use git. With write-blocking options, **81 tests passed**. The in-memory trials below were done on FakeRail; real Braintree was not run.

12 findings, in order of importance:

1. **High — `void` bypasses the refund checks entirely.**  
   **Where:** `counterfoil/gateway.py:147`, `:275`  
   Only ownership is checked; the Reader's transaction type and order are not compared.  
   **Trigger → result:** In a `CLEAN-01` refund context, `void(order_no="ST-1058")` → `PASS`, another order's 50 dollar transaction was voided. **Verified.**  
   **Fix:** Require an explicit transaction intent and an order match for a void; also check the full amount to be voided. Refund authority must not automatically be full void authority.

2. **High — A hard block can be downgraded to human approval by changing the RMA id.**  
   **Where:** `counterfoil/gateway.py:172`, `:298`  
   The `unknown/pending` check runs only on the existing RMA that the call chose.  
   **Trigger → result:** For `ST-1051`, which has an unknown refund, `rma_id="invented", amount="50"` → only `RMA_MISSING`; once approved, a new refund goes through. **Verified.** This is not an automatic pass; it is a bypass of a block that "cannot be overcome even with approval".  
   **Fix:** Make RMA validation mandatory; also check unlinkable or unknown refunds at the transaction/order level. Tie exceptional refunds to a separate, traceable authorisation.

3. **High — Concurrent approvals can exceed the RMA balance.**  
   **Where:** `counterfoil/gateway.py:102`, `:302`  
   In the atomic section, `human_approved=True` removes the whole balance check; which exception the human approved is not distinguished.  
   **Trigger → result:** On a 30 dollar RMA, two 20 dollar requests pending only because of a currency mismatch; I made the check phase of the two approvals run concurrently → both executed, total **40 dollars**. **Verified.**  
   **Fix:** Store the approved exception and the monetary limit. Re-check the current balance during reservation; a new balance violation must not be counted as covered by the earlier approval.

4. **High — TTL does not apply in the default approval call.**  
   **Where:** `counterfoil/gateway.py:84`, `:98`  
   The time check uses the unchanging `ctx.as_of` instead of the real clock.  
   **Trigger → result:** A pending request whose context time is 100 days old → `approve(id)` still works. **Verified.** The existing TTL test passes because it only tests the path where `now` is passed in from outside.  
   **Fix:** Use a trusted current UTC time at creation and at approval; swap the same clock provider in tests.

5. **High — Persistence and reconciliation with the rail are missing from the default flow.**  
   **Where:** `counterfoil/store.py:57`, `:72`, `counterfoil/gateway.py:180`  
   The default SQLite is in memory; the checks look only at local refund rows. Existing refunds on the rail are not read.  
   **Trigger → result:** 30 dollar refund → new `Store` with the same fixture → another 30 dollars to the same RMA `PASS`; 60 dollars in total. Also, a 30 dollar refund made on the rail from outside did not stop the local call. **Both verified.**  
   **Fix:** A persistent DB should be mandatory in the running application. Import external refunds; for movements that cannot be linked to an RMA, stop automatic refunds until reconciled. The real application's DB configuration was **not verified**.

6. **Medium — An accepted refund is recorded as if settled.**  
   **Where:** `counterfoil/gateway.py:312`, `counterfoil/rail.py:74`  
   `res.ok` is treated as enough; a `submitted_for_settlement` result becomes `completed` directly.  
   **Trigger → result:** 10 dollar refund on a 30 dollar RMA → `completed` in the DB while the rail result is not yet settled; a second 10 dollars also goes through. **Verified.** The draft's "reconcile if there is a pending one" behaviour is not implemented. If it later fails, the entitlement stays consumed.  
   **Fix:** Separate the accepted, pending, settled and failed states; update them by webhook/lookup. Later failure on the real rail was **not verified**.

7. **Medium — The Reader's empty fields are accepted as matching.**  
   **Where:** `counterfoil/gateway.py:245`, `:251`  
   A missing contract or critical field produces no mismatch.  
   **Trigger → result:** In a `CLEAN-01` context, `reader={}` → refund `PASS`. **Verified.** If the Reader did not name an order/RMA, the agent can pick the customer's other open records; the intent comparison does not work.  
   **Fix:** Validate the mandatory Reader fields per transaction type; for missing fields, ask for approval instead of passing automatically. That an attacker can change the Reader contract directly was **not verified** here; it happens when an open, incomplete contract arrives.

8. **Medium — Charge failure and uncertainty are not distinguished; a legitimate retry gets locked.**  
   **Where:** `counterfoil/gateway.py:286`, `counterfoil/store.py:143`  
   `charge_seen()` counts every row as a duplicate regardless of status. On an exception the record stays `requested`; the rail transaction id is not stored either.  
   **Trigger → result:** A definite failure `RailResult(False)` → a retry from the same email gives `DUPLICATE_CHARGE`. **Verified.** There is also not enough record to resolve whether the charge happened after a timeout.  
   **Fix:** Allow a controlled retry on definite failure; reconcile on uncertainty. Store the rail id and attempt states persistently.

9. **Medium — The argument schema does not stop type confusion and uncaught errors.**  
   **Where:** `counterfoil/gateway.py:239`, `counterfoil/money.py:26`  
   Quantities are truncated with `int()`; `quantize()` errors are outside the scope of `BadAmount`.  
   **Trigger → result:** 3 BAG in the Reader, `qty=3.9` in the call, amount 120 → `PASS`. `amount="9"*40` → an uncaught `InvalidOperation` instead of `BLOCK`. **Both verified.**  
   **Fix:** Validate quantities as positive, non-bool integers; set a length/upper limit on money and turn Decimal errors into controlled rejections. Use ids with the same canonical type in checking and in execution.

10. **Medium — The currency is not bound to the approved transaction.**  
    **Where:** `counterfoil/gateway.py:229`, `:287`, `counterfoil/rail.py:126`  
    The currency is compared but not carried to the rail interface; the charge adapter does not pick a matching merchant account.  
    **Trigger → result:** In a USD configuration, an EUR charge request is approved → only the amount/token go to the rail; the EUR request cannot be applied. **The loss of the argument was verified from the code; the real charge currency was not verified.**  
    **Fix:** Block unsupported currencies, or carry a verified merchant account mapping into execution. The currency shown on the dashboard and the one executed should be the same.

11. **Medium — The "did not reach the rail" test does not really verify this.**  
    **Where:** `tests/test_scenarios.py:35`, `counterfoil/gateway.py:309`  
    The test only says `not out.executed`; this field represents a successful rail response.  
    **Trigger → result:** FakeRail first refunded 30 dollars, then timed out → although the real balance changed, `decision=PASS`, `executed=False`, findings show `BLOCK/RAIL_ERROR`. **Verified.** The condition the test uses counts this result as safe.  
    **Fix:** Verify the number of rail calls and the final state separately. Distinguish `attempted/succeeded/unknown`; do not count an unknown result as harmless. In clean scenarios too, test not only the decision but the completion of the expected work.

12. **Medium — The baseline comparison is not clean; there is a risk of inflation in our favour.**  
    **Where:** `counterfoil/baselines.py:15`, `:28`, `counterfoil/rail.py:79`, `tests/test_scenarios.py:48`  
    `NoGate` inherits the charge duplicate check from Gateway; it is not "direct rail". In the other direction, FakeRail does not model at all the rail's duplicate-sale rejection observed in the document. Also, the test does not check that CapGate really stops when `cap_200_would_block=True`.  
    **Trigger → result:** Close charges with the same token/amount from separate sessions → FakeRail accepts both; counting these as "the rail missed it" may be in our favour. In the same session, the protection NoGate inherits shrinks the difference. **The code behaviours were verified; how much the current results are skewed numerically was not verified.**  
    **Fix:** Separate the shared executor from the policy checks; define the baseline scope explicitly. Measure the rail's duplicate behaviour separately and test both directions of the expectations.
