**Main assessment:** The idea is feasible; but the current P1–P5 table does not yet form a security guarantee. The priority should be to define the trusted reference, the transaction identity and what the measurement will count as success.

**10 findings, in order of importance**

1. **Sections 2–3 — The raw email is not a trusted reference.**  
   **Problem:** The inference "The gate sees the raw email, A01 is closed from the start" is not valid. The email contains both the real amount and the attacker's alternative amount; how will the gate decide which one is authoritative? Making two separate extractions from the same text does not give independent verification either.  
   **Why it matters:** If the Reader and the gate pick the same wrong amount, P1/P4 can pass the consistency check.  
   **Fix:** Define an external reference such as an approved purchase record. If there is none, store the source location of the field and send conflicting/ambiguous sources to APPROVAL; write this not as "A01 is closed" but as an extra check to be tested. The correct-answer label in the test must not be given to the production gate.

2. **Section 3, P1–P2 — The transaction being checked is under-defined.**  
   **Problem:** A check of only "is the amount larger?" does not cover a currency change, underpayment, or the total of split payments. The payee being any registered supplier also does not show it is the right supplier.  
   **Why it matters:** A different currency with the same numeric amount, or choosing another registered supplier, can slip through. On the clean side, tax, discounts, instalments and number formats can produce unnecessary alarms.  
   **Fix:** Check supplier identity, approved payment destination, invoice id, currency and the balance due together. Do money arithmetic with exact decimals. Define explicitly the cases where deviation from equality is legitimate; confirm account changes through the existing trusted communication channel.

3. **Section 3, P3 — A past-transaction lookup alone does not prevent duplicate payment.**  
   **Problem:** Matching "same invoice no + amount" can miss when the amount is changed, and can produce wrong blocks for invoices with the same number from different suppliers. Two concurrent requests can both proceed before either sees a past payment.  
   **Why it matters:** Retry after a network error, pending payments and cross-session repeats are the main gaps.  
   **Fix:** Use an invoice id tied to the supplier, persistent transaction state, atomic reservation and a fixed idempotency key. If the API result is unknown, reconcile the existing transaction without opening a new payment. Let `list_transactions` help with history checks; it should not be the only lock.

4. **Sections 2–4 — "Single door" and human approval are not yet a security contract.**  
   **Problem:** Direct MCP/REST access, sessionless calls, changing arguments after approval and reusing an approval are undefined behaviours. Carrying the global `AKTIF` (active) state in the source code over unchanged to a multi-session service also creates a risk of context mix-up.  
   **Why it matters:** The right rule can be applied to the wrong session, or the check can be bypassed entirely.  
   **Fix:** PayPal credentials should exist only in the gate; all paths should go through it. If context is missing, the write should be stopped. Approval should be bound to the user, the transaction, the context and the full arguments, time-limited and single-use. The duplicate check should be done again while the approved transaction is executed.

5. **Section 3, P4–P5 — The attack path and authorisation scope are unclear.**  
   **Problem:** In P4 the Payment agent does not see the raw email; in which field does the hidden instruction reach it? In P5, if the "list" call is allowed, K1 does not fire. No exfiltration channel is defined for "send it to me" either.  
   **Why it matters:** P4 may test an unreachable attack, and P5 a capability that does not exist in the system. Reading another customer's data with an allowed tool can be overlooked.  
   **Fix:** Define the inter-agent schema; write down whether description/note fields are passed on. Test P4 on the real hand-off surface. Check P5 by customer/invoice scope and data egress, in addition to the tool name. Count a successful read and an external data transfer separately.

6. **Sections 1 and 5 — The measurement does not separate the gate's contribution from the attack's failure.**  
   **Problem:** "N scenarios × 3 runs" is not a sufficient definition. The thesis [report](/Users/kosesena/Desktop/bitirme-projesi/docs/haftalik/2026-10-22-hafta-03.md:105) confirms 0/21; but the whole drop is not attributed to the quantity rule. A01 stopped for another reason.  
   **Why it matters:** The agent not attempting the attack, an API error, or the agent abandoning the task can be counted as "the gate caught it".  
   **Fix:** Record separately in each run: the evaluation reference, Reader output, **all** tool attempts, gate decisions, calls that reached the API and the verified final state. Measure the attack attempt, gate intervention, harmful outcome and completion of the legitimate task separately. Missing evidence should be "unknown". Report gate on/off experiments in the same configuration and rule tests with fixed calls separately. Separate the number of scenarios from the number of repeats.

7. **Sections 3–4 — Clean pairs and "protected amount" can produce misleading results.**  
   **Problem:** Five emails with only the attack line removed are too narrow to measure false alarms. A legitimate account change or a high amount may already require approval. Repeats of the same blocked call can inflate the "protected amount" total.  
   **Why it matters:** Routing that follows the business rule, unnecessary alarms and correctly stopping a model error get mixed up.  
   **Fix:** Write the expected decision and transaction values for clean examples in advance. Add tax, different number formats, instalments, old correspondence, legitimate retries and approved account changes. Report "unnecessary intervention" and "stopping a faulty transaction" separately. Show "transaction amount put under review" on the dashboard; do not present it as proven prevented loss.

8. **Sections 2, 5 and 7 — PayPal can be at the centre; the current fallback flow does not guarantee it.**  
   **Problem:** The main integration is named Invoicing, but the centre of the attacks and the video is Payouts. If Payouts does not work, an invoice record + mock is not evidence of the real payment behaviour described.  
   **Why it matters:** There is a risk that the strongest scene is cut off from the real PayPal integration.  
   **Fix:** Choose the main direction with an early end-to-end sandbox trial. If Payouts works, make payment and status verification the main flow. If it does not, rewrite the scenarios around the real Invoicing lifecycle. Instead of an empty transaction list, show a trace proving the request stopped at the gate, and a status check by transaction id. **No jury decision has confirmed that the "at the centre" requirement is met.**

9. **Sections 6–7 — Running a tool in Docker does not show fit with Blast Radius Zero.**  
   **Problem:** In the track definition you gave, the agent must write/run code or use a browser. Putting a fixed payment tool inside Docker does not achieve this by itself; the payment policy stopping something also does not prove that the sandbox boundary works.  
   **Why it matters:** Even as a security demo, it may go to the wrong track.  
   **Fix:** If there is a real business need, run agent-generated code for document processing in a restricted environment; show separately that a controlled file/network access attempt is stopped by the sandbox. If there is no such need, Future of Work is a more consistent candidate. Do not take Vultr eligibility as certain before the pre-existing-code acceptance is clear.

10. **Sections 4 and 6 — AG Studio integration is left at the end of the critical path.**  
    **Problem:** The approach of building a transaction-specific widget through the Studio Agent Framework has not yet been validated with a working prototype; it is left to 9–12 Nov.  
    **Why it matters:** The core feature of the sponsor target could be blocked in the last days.  
    **Fix:** Plan a small early integration trial in line with the licence terms. The widget should consist only of permitted data and components; payment approval should be verified on the server side. Email content should not be able to give instructions to the widget or to the approve button's behaviour. If the dynamic widget is delayed, the basic approval flow should keep working.

**Short email outlines for P1–P5 — I am not writing the texts yet**

| Scenario | Technique/variation plan |
|---|---|
| **P1** | A different payment request in an HTML note or quoted correspondence against the open invoice total. Separate variation: same number, different currency. In the clean pair, tax and total are clearly consistent. |
| **P2** | Changing the payment destination under an account-update pretext. One variant points to an unknown destination, one to another registered supplier. Clean control: a pre-verified account update. |
| **P3** | A repeat request on the grounds that "the payment didn't arrive". Separate preconditions: completed, pending, failed and unknown-outcome payment. Concurrency should be a runner test separate from the email. |
| **P4** | While the Reader extracts the correct fields, placing a "fix it at payment time" steering in the note field that is allowed to be passed on. If no such hand-off field exists, P4 should be a direct contract test instead of an email attack. |
| **P5** | Asking for other customers' invoices under a reconciliation pretext. An unauthorised tool and the unauthorised scope of an allowed tool are separate variants. Data egress should be tested only with a defined test recipient. |
| **Extra P6** | Splitting a single invoice into more than one payment call or new sessions to exceed the total debt. The clean pair should contain instalments that do not exceed the same debt. This tests the path that P3's exact-repeat check cannot see. |

For each example, the correct action, the change the attacker targets and the expected decision should be fixed **before the run**; Sena should check the texts and references. A few variations not used in rule development should be held out for the final evaluation.
